# Rendering reliability and remote browser options

The collector must prioritize fresh observations and exports. Native image operations and Chromium can fail independently of HTTP serving. Thread exhaustion can also come from process/PID limits; low RSS alone does not rule it out.

Production uses one Railway service/replica with a persistent `/data` volume. The memory limit is 2 GB with 1 vCPU. The renderer defaults to the final 1200×1200 resolution instead of drawing 2400×2400 and downsampling. This reduces raster pixels by 75%; it is not a claim of a 75% reduction in total process memory.

Collection runs observation, detection, exports and a lightweight enqueue command. A separate background scheduler processes media, publishing and archives sequentially, so Chromium and FFmpeg never block the collection scheduler. Both lanes have bounded child lifetimes and process-group cleanup. Schedule refresh waits for current background work before replacing shared GTFS files. Low disk space and stale required sources pause new background work. Tini remains PID 1; Sharp/libvips, libuv and FFmpeg concurrency and frame staging remain bounded.

`media_jobs` in the existing SQLite WAL database stores deduplicated work and retry state. The worker claims one job at a time with a three-minute lease (longer than its two-minute process deadline). Interrupted work recovers after lease expiry. Failures back off for 1, 2, 4 and 8 minutes, then stop after five attempts. Fresh incident images precede hourly analytics, existing-image repair and optional videos. Analytics use an hourly revision; pending/running payloads cannot be replaced under the worker. Rendering never holds a database transaction. Completed/failed queue rows retain 90 days; delivery receipts and source incidents are independent.

Only successful street basemaps are cached under `/data/state/basemaps`, keyed by viewport, dimensions, scale, style and renderer/MapLibre version. Overlays are composited afterward so a cache hit cannot reuse old vehicle positions. The cache expires after seven days and is capped at 64 MiB. No credentials appear in cache keys or logs. Existing media remains available during repair; unversioned images among the most recent 200 incidents are queued for refresh without deleting videos or receipts.

Media indexes add `renderer_version`, `basemap` (`street`, `geometry` when no provider is configured, or `degraded` after a provider/browser failure), `render_error` (a safe category), and `rendered_at`. Videos add `video_basemap` and `video_renderer_version`. A degraded still image is saved as a labeled fallback and retried; a video requiring a street basemap is retried without marking it checked. These fields also flow through the existing incident/analytics exports. A worker completing successfully does not imply every queued render succeeded: inspect queue outcomes and failures.

`/healthz` remains liveness. `/readyz` requires fresh collection and all three required source timestamps. `/api/health` exposes separate `running` and `background_running` jobs, `last_cycle_duration_ms`, queue counts/oldest pending time/cumulative outcomes, and Linux cgroup memory current/peak/limit/events alongside PID metrics. `/metrics` includes queue pending/failed gauges and cgroup OOM kills. The health of source collection remains separate from optional media health. No historical observations can be recovered merely by restarting.

## Does this require Cloudflare?

No. Lifecycle, resource bounds, failure isolation and monitoring are required regardless of browser location. Offloading Chromium would remove its resource demand from the collector, but Sharp/libvips, FFmpeg and orchestration still require safeguards.

Cloudflare's service is now called Browser Run. It supports direct Playwright/CDP from an existing Node server as well as a Worker with a browser binding; a custom Worker is optional. [Integration guide](https://developers.cloudflare.com/browser-run/get-started/), [Playwright/CDP](https://developers.cloudflare.com/browser-run/cdp/playwright/).

A promising follow-up is an authenticated render Worker: accept a bounded route/viewport specification, serve pinned MapLibre assets from the Worker, render to PNG, and return the image. Railway keeps collection, SQLite and archives. The current renderer serves modules on 127.0.0.1, which a remote browser cannot reach; simply replacing `launch()` with `connectOverCDP()` will not work. Alternatively, intercept the remote page's requests and fulfill the fixed local assets through Playwright. Preserve map attribution and use a render-complete signal with a deadline.

Use a private authenticated endpoint, payload/viewport limits, allowed resource origins, single-flight requests and a cache keyed by geometry, style and renderer version. Keep API credentials server-side and redact them from logs. Explicitly close sessions, handle 429/Retry-After and timeouts, and retain the labeled geometry fallback. Avoid arbitrary client-supplied navigation URLs.

Cloudflare reports WebGL support, making MapLibre plausible, but this exact MapLibre version, fonts, workers and image quality still require a real rendering proof of concept. [Cloudflare's platform update](https://blog.cloudflare.com/browser-run-containers/).

Free usage includes 10 browser minutes/day and three concurrent sessions. Paid usage includes 10 browser hours/month, then $0.09/hour, with 10 average concurrent sessions included and $2 per additional average concurrent browser. Workers plan and other infrastructure charges are separate. Paid concurrency's default limit is 200; the normal browser timeout is 60 seconds of inactivity. Close sessions promptly rather than keeping idle browsers alive. These are published terms checked November 10, 2026, not a measured cost estimate for this app. [Pricing](https://developers.cloudflare.com/browser-run/pricing/), [limits and lifecycle](https://developers.cloudflare.com/browser-run/limits/).

Before rollout: measure render count/duration and cache hit rate; test Protomaps failures, missing tiles, 429s, remote disconnection and invalid payloads; compare real route renders and attribution; then soak-test process counts and fresh collection through many render/retry cycles. No Cloudflare resources or credentials were provisioned as part of this research.

## Validation and release gate

The Node 24 release gate runs runtime/queue/cache/render tests, the full collector and frontend suites, both workspace lints, the frontend build, and the Linux Docker build in CI. Queue tests cover restart recovery, retry exhaustion, deduplication, payload isolation, priority and preservation of existing media/receipts. A slow background-child test verifies continued collection and graceful shutdown.

Local real-geometry verification renders Route 04 with streets and attribution at 1200×1200. A single measured cold render took 2.96 seconds and the repeated cached render 0.13 seconds; these are smoke checks, not load benchmarks. Docker is unavailable locally, so the CI container build must pass before merge. After deployment, verify the exact merge commit, fresh feed timestamps, successful enqueue/background jobs, newly generated `renderer_version: 2` street images, queue progress and no new cgroup OOM kills. Continue evaluating a 24-hour window before claiming long-term rendering reliability or deciding to offload Chromium.
